한 줄 요약

DeepSeek Harness는 plugin 조합과 세션 로그를 중심으로 에이전트 실행 환경을 분해하는 Developer Preview 런타임이지만, 현재는 Hermes를 바로 대체하기보다 구조 관찰 대상으로 보는 편이 정확하다.[1]

조사 배경

DeepSeek Harness 공식 저장소·소개 페이지와 추가 분석 문서를 대조해, 모델과 harness의 경계, plugin 구조, sandbox·세션 로그의 역할을 확인했다. Gemini 분석 문서에 포함된 수치 중 공식 근거가 연결되지 않은 항목은 확정 사실로 사용하지 않았다.[1]

확인한 내용

  • dsh는 단순한 DeepSeek CLI가 아니라 모델·도구·스킬·세션·sandbox·storage·agent loop·UI를 교체 가능한 plugin으로 조합하는 agent harness로 설명된다.[1]
  • 하부 구조는 Cordis를 중심으로 하며, profile·bundle·patch layer를 조합해 web·headless·실험용 구성을 나누는 방식이다.[1]
  • 세션 로그는 대화 history뿐 아니라 tool call/result, resume·fork, transcript·replay, telemetry·persistence의 컨텍스트 원천으로 취급된다. 모델에게 보인 내용은 로그에서 재구성 가능해야 한다는 원칙이다.[1]
  • 공식 실행 경로로 Node.js·pnpm과 npx @deepseek-ai/dsh web이 제시되어 있고, 기본 로컬 웹 포트는 3080으로 기록되어 있다.[1]
  • sandbox는 파일 효과 정책을 중심으로 하며, network와 process visibility를 자동으로 보장하는 전체 보안 경계로 설명되지 않는다. read-only, workspace-write, danger-full-access 구분도 이 범위에서 이해해야 한다.[1]

아직 확인하지 않은 내용

  • dsh를 실제로 설치하거나 직접 benchmark하지 않았다.[1]
  • DGX Spark GB10 ARM64에서 Node.js·pnpm·native dependency·sandbox backend가 완전히 호환되는지 확인하지 않았다.[1]
  • 추가 분석 문서의 1M context, 95% prefix cache, 비용 절감 및 커뮤니티 plugin 수치는 동일 조건의 공식 benchmark 또는 재현 가능한 실측으로 확인하지 않았다.[1]
  • Developer Preview의 호환성 파괴 변경 가능성과 plugin 공급망·권한 범위를 운영 환경에서 검증하지 않았다.[1]

다음 실험/검증 계획

  1. 공식 저장소의 고정 commit에서 source와 package lock을 확인한다.
  2. 기본 web profile의 plugin tree와 --dump-config 결과를 기록한다.
  3. read-only 또는 workspace-write로 최소 작업을 실행하고, network·process visibility가 별도로 통제되는지 확인한다.
  4. session log에서 model-visible context와 tool result가 재구성되는지 확인한다.
  5. custom plugin은 하나씩 추가하면서 권한·네트워크·로그를 검증한다.[1]
