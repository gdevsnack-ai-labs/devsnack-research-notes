한 줄 요약

OMH는 Hermes를 대체하는 새 에이전트가 아니라 workflow·routing·handoff·evidence 경계를 보강하는 운영 레이어이며, 별도 profile의 core 설치와 작은 A/B 검증부터 시작해야 한다.[2]

조사 배경

이름이 같은 여러 저장소 중 rlaope/oh-my-hermes를 기준으로 공식 README·설치·아키텍처 문서를 대조했다. 기존 Hermes 환경의 설정·provider·Hindsight 메모리를 보존하면서, OMH가 실제 실행 증거를 만드는 시스템인지 아니면 운영 지침과 handoff를 제공하는 레이어인지 구분하는 것이 조사 범위였다.[2]

확인한 내용

  • OMH는 Hermes의 자연어 대화·기본 스킬·native delegation을 유지하면서 요청 분류, 계획, coding handoff, 상태 표시와 evidence boundary를 보강하는 로컬 운영층으로 설명된다.[2]
  • 원문 기준 패키지는 Python 3.11 이상·MIT로 선언되어 있고, 현재 소스에서 102개 skill 디렉터리와 8개의 ulw- workflow가 확인됐다. 이 숫자는 성능 benchmark가 아니라 설치 카탈로그 규모다.[2]
  • Plan · not run, Code · running, Code · reported done, Test · verified처럼 준비·실행 보고·검증을 구분하는 상태 계약을 제안한다.[2]
  • full profile은 넓은 skill과 workflow를 포함하고, --core는 router·plan·status·handoff·doctor 같은 최소 운영 표면으로 시작하는 경로다.[2]
  • 모델 routing 추천은 benchmark 순위가 아니라 편집 가능한 운영 정책이다. 초기 도입에서는 현재 모델·provider와 Hindsight를 그대로 보존하는 것이 원문의 권장안이다.[2]

아직 확인하지 않은 내용

  • 현재 Hermes v0.20.2 환경에는 OMH를 설치하지 않았고, 실제 handoff도 실행하지 않았다.[2]
  • OMH 공식 호환성 표와 Hermes v0.20.2·DGX Spark GB10 ARM64 조합의 직접 실행 결과를 확인하지 않았다.[2]
  • omh doctor가 현재 profile의 기존 설정과 skill 등록을 정상적으로 확인하는지 검증하지 않았다.[2]
  • OMH의 모델 routing이나 full profile이 실제 문맥 비용·latency·검증 누락률에 어떤 영향을 주는지 측정하지 않았다.[2]

다음 실험/검증 계획

  1. 현재 Hermes 설정·provider·메모리 상태를 기록한다.
  2. OMH 소스를 commit SHA로 고정하고 별도 Hermes profile에서 omh setup --core와 omh doctor를 실행한다.
  3. 모델 alias·provider routing을 바꾸지 않고 작은 handoff 1건을 실행한다.
  4. OMH 미사용·core·full의 첫 응답 시간, 총 turn 수, tool call 수, 검증 누락률, 실패 복구, 문맥 비용, 사용자 개입 횟수를 비교한다.
  5. 실제 사용 가치가 확인된 workflow만 단계적으로 추가하고, full profile과 모델 routing 확대는 재평가 후 결정한다.[2]
